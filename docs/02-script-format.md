# 02 · 脚本格式

## 1. 解压后的结构

脚本条目解压后是「指令流 + 内联文本」的混合结构，没有任何全局头部。

```
指令 4 字节:  [u8 opcode][u24 param]        小端
常见 opcode:  0xA0 0xA1 0xA2 0xA3 0xA4 0xA8 0xAA 0xAB 0xAC 0xAD
             0x000000 视为 nop
```

文本不是独立资源，而是**内联在 `0xAA` 指令后面**：

```
AA 00 <index:u16 le>  +  Shift-JIS 文本  +  [00 00]  +  AB 00 00 00
 ^^^^^^^^^^^^^^^^ 4 字节头
```

关键：**文本没有长度字段**。解析器只能「一直读到第一个非法 Shift-JIS 字节」。
判定规则：

```
0x00                        -> 结束
0x81..0x9F / 0xE0..0xEF + 后续字节在合法范围  -> 双字节字符，跳过 2
0x20..0x7E                  -> 单字节 ASCII，跳过 1
其他                        -> 结束
```

`index` 是该文本的编号（同一脚本内唯一），调试时可以靠它对上原文。

## 2. 解析

```bash
python tools/script_tool.py parse dec.bin > entries.json
```

输出每条文本的：

```json
{ "index": 12, "hdr_off": 1234, "text_off": 1238,
  "text_len": 46, "tail": 2,
  "sjis": "……原文……", "raw_hex": "..." }
```

- `hdr_off`：`AA 00` 指令起始位置
- `text_off`：文本起始位置
- `text_len`：原文**字节数**（不是字符数）
- `tail`：文本后紧跟的 `00 00` 数量（0 或 2）

## 3. 回写策略：定长替换

中文（GBK）通常比日文（Shift-JIS）短，所以用**定长覆盖**：

```
新文本字节数 <= 原文本字节数
剩余空间用 0x00 填充
```

好处：后续所有指令、跳转偏移、`index` 都不用重算 —— 整个脚本长度不变。
代价：超长译文无法写入，需要「吃掉尾部空指令 / 排版压缩」等技巧（见 `06`）。

```bash
python tools/script_tool.py apply dec.bin trans.jsonl out.bin
# trans.jsonl: {"off": 1238, "text": "译文"}
```

`apply` 会做三件事：

1. 按 `text_off` 定位原文；
2. 校验 GBK 编码长度 ≤ 原字节数（超长直接报错，不静默截断）；
3. 写入 + 补零。

## 4. 编码选择

| 环节 | 编码 | 理由 |
|---|---|---|
| 原文读取 | CP932（Shift-JIS） | 引擎原生编码 |
| 译文写入 | GBK（CP936） | 与自绘字库的字符集一致；且单字 2 字节 |
| 字库码位 | JIS 汉字区 | 见 `03` |

GBK 与 Shift-JIS 都是双字节，字节长度一一对应，这是定长替换可行的前提。
但要注意：GBK 的标点、全角字符与 SJIS 宽度一致（都是 2 字节），ASCII 段一致（1 字节），
所以只要原文/译文都用对应编码，字节数比较是有意义的。
