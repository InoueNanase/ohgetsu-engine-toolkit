# 01 · PAC 容器与 LZSS 压缩

## 1. 容器结构

`SCRIPT.PAC` / `VISUAL.PAC` / `SE.PAC` 等归档文件本身**没有索引头**。
索引表写在 `SilveryWhite.exe` 内部（`ExeEntry` 数组）：

```c
struct ExeEntry {          // 8 字节
    uint16_t is_compressed;   // 0 = 原始数据, 1 = LZSS 压缩
    uint16_t resource_id;     // 资源编号（脚本/图片/音频等）
    uint32_t offset;          // 在 .PAC 内的偏移
    uint32_t length;          // 压缩后（落盘）长度
};
```

要点：

- 条目按 **2048 字节对齐**，条目之间可能有填充。
- 表本身在 EXE 的 `.data`/`.rdata` 段，靠「offset/length 的单调性与对齐规律」可以定位。
- 同一个 EXE 对应同一批 PAC，换版本（如修正版）偏移会变，**不要硬编码跨版本使用**。

## 2. 条目格式（LZS）

压缩条目：

```
偏移 0   : "LZS\0"          (4 字节魔数)
偏移 4   : uint32 解压后大小  (小端)
偏移 8   : LZSS 压缩流
```

未压缩条目直接是原始数据（`is_compressed == 0`）。

## 3. LZSS 参数

经典 Okumura 实现，参数如下：

| 参数 | 值 | 说明 |
|---|---|---|
| `N` | 4096 | 环形缓冲区大小 |
| `F` | 18 | 最大匹配长度 |
| 初始填充 | `0x20` | 空格（0x20），保证每次匹配都合法 |
| 写指针初值 | `4078` | `N - F` |
| 标志位 | 1 字节 / 8 个 token | **低位优先**，`1` = 字面量，`0` = 匹配 |
| 匹配编码 | 2 字节 | `pos = b1 \| ((b2 & 0xF0) << 4)`（12 位绝对环形位置）<br>`len = (b2 & 0x0F) + 3` |

注意 `len` 是**绝对环形位置**而不是回退距离 —— 这是最容易写错的地方。
解码时用 `buf[(pos + k) & (N - 1)]` 逐字节复制，同时把结果写回环形缓冲区。

最小匹配长度是 3（`THRESHOLD + 1`），所以长度字段能表示 3..18。

## 4. 参考实现

`tools/lzss.py` 同时提供解压与压缩：

```bash
python tools/lzss.py d input.bin output.bin        # 自动识别 LZS\0 头
python tools/lzss.py c raw.bin packed.lzs          # 生成带 LZS\0 头的条目
python tools/lzss.py t                             # 自检（往返一致性）
```

压缩器使用 3 字节前缀索引做候选搜索，再逐字节验证，输出与官方压缩流
**不保证字节一致**，但解码结果完全等价 —— 游戏端只要求是合法 LZSS 流。

## 5. 落盘回写

替换脚本条目时的顺序：

1. 解出所有条目 → 修改目标条目；
2. 重新压缩 + 重排 `offset`（保持 2048 对齐）；
3. 同步更新 EXE 里的 `ExeEntry` 表 —— **这一步必须一起做**，否则读到的还是旧偏移。

如果只是**定长替换**（见 `02-script-format.md`），压缩后长度通常变化不大，
但仍建议整体重排后一次性写回 PAC 并更新索引表。
